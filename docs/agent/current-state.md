# Current State

Last updated: 2026-07-24

## Product phase

CanCan has crossed from documentation/design alignment into production implementation. The app foundation, synthetic core flow, production Vault storage, first user-facing manual-evidence path, and mock-only cloud OCR provider contract are complete. A reusable cloud OCR transport executor with deterministic mocked transport tests is in progress; app/runtime wiring, a live-provider smoke, and broader financial behavior have not started.

The current product target is an inbox-first local financial evidence vault and polished personal finance/account-record workspace with AI-assisted parsing, deterministic validation, policy-gated ledger commit, and source-backed money views. Add/Open With, a user-selected Inbox folder, and optional Gmail all converge on the same evidence pipeline; Gmail is not required for first use. MVP has no hosted service/backend; Gmail, BYO AI, optional fixed FX rates, update checks, and future connectors are capability-scoped local-client connections controlled by the user. An optional paid CanCan AI relay is an allowed post-MVP direction only; it must reuse the provider-adapter/capability boundary and has no current runtime, account, payment, or entitlement implementation.

## Implementation state

- The repository contains a real pnpm workspace with a React/Vite desktop shell, Tauri/Rust runtime, pure TypeScript core and parser packages, a slice-owned SQLite repository/migration boundary, a reusable UI package, and a disposable desktop feasibility spike. Production packages do not import the spike.
- Root typecheck, production unit-test, Rust-check/test, web-build, Tauri debug-build, fast verification, native verification, and combined local verification commands are real. Pull requests and `main` run the fast typecheck/unit/web gate on Linux; only ready native/sidecar/parser/migration/toolchain changes run the Rust security/data-integrity and desktop-build gate on macOS. The native and combined orchestrators build the sidecar once and reuse Cargo outputs; standalone Rust and desktop-build commands remain self-contained. Isolated spike tests remain in their owning workflows.
- The foundation UI has been replaced by a visually inspected desktop/narrow manual-evidence checkpoint. It invokes only narrow Tauri Vault/status/remembered-unlock/import/routing/source-list/document-list/view/export commands and exposes no network, database, secret, filesystem path, hash, locator, raw original-file byte payload, or unbounded extracted document-content response to the renderer. The general Money Source list returns only stable ID, display name, and source type; routed documents load only for the selected source ID. The PDF/PNG/JPEG viewer receives only bounded in-memory rendered PNG pixels plus page position; CSV evidence receives at most the first 200 lines and 32 KiB of UTF-8 preview plaintext, which may contain all text when a small file fits within both caps; `Save a copy` returns only cancellation or completion after the host-owned warning, picker, and write.
- The synthetic-core harness safely resets only marked test databases, reapplies its migration idempotently, validates deterministic structured proposals against coherent raw rows, and exercises review, source-backed balance observations, exact transfer reconciliation, atomic commit, immutable audit, idempotency, and bidirectional record/event navigation. It uses no live model, network, vault, or production document.
- The `desktop-feasibility` slice is complete. ADR 0001 is accepted after a real Tauri 2, SQLCipher/FTS5, authenticated-file-encryption, Argon2id wrapper, and macOS Keychain smoke test.
- The `app-foundation` and `vault-security-validation` slices are complete. The accepted version-1 envelope, KDF selection, Keychain scope, memory-only viewer boundary, deletion recovery, and restore locator switch have reproducible macOS `arm64` evidence before production Vault implementation begins.
- Rust-owned extraction-bundle observation strings and serialized command bytes are zeroized when their job-scoped buffers drop. The short-lived sidecar exits after each request, and no extraction bundle is persisted; this does not claim that PDFKit, Foundation, Node.js, or operating-system allocators erase every transient plaintext copy.
- The `synthetic-core-flow` slice is complete. Its schema and repository cover only exercised synthetic queries. `vault-manual-import` is complete: the production Rust host includes the canonical migrations, opens SQLCipher with a context-separated raw database subkey, writes `CCENV001` files, and coordinates exact-hash import outcomes with store-open/rollback recovery logic. App startup acquires exclusive OS-backed process ownership before constructing the Rust-only locked/unlocked Vault session, so a second process fails closed before open-time reconciliation or mutation. The accepted Argon2id password wrapper recovers the master key without returning it to the renderer. Creation prepares and syncs an inactive candidate before rename, rolls back handled activation failures, and can reopen an activated Vault after restart. An abrupt pre-activation process crash may leave an inactive `.vault-create-*` directory; automatic cleanup remains deferred even though the ownership boundary now prevents cleanup beneath a second app process. Host-picked PDF/CSV/PNG/JPEG import no longer accepts a Money Source, account, or semantic identity and captures both identity fields as null while retaining immediate SHA-256 deduplication. A trusted Tauri command creates job-scoped PDFKit native-text or deterministic CSV table-cell observations from the current decrypted in-memory document, sends the strict extraction bundle to the bundled single-pass mock sidecar, verifies the synthetic provider fingerprint, and transactionally resolves exactly one configured Money Source plus stable provider account IDs. On macOS, every PDF page keeps its native observation first; local Vision revision 3 accurate OCR runs only for empty/whitespace text or NUL, U+FFFD, or non-layout control markers, reuses the in-memory Core Graphics page renderer, and appends separately provenance-tagged OCR observations with canonical top-left unit-square boxes. OCR page pixels, PNG bytes, and intermediate recognized strings use zeroizing Rust-owned buffers. OCR failure or a missing Vision result collection rejects a page with no usable native content; when usable non-empty native text remains alongside a broken marker, failed supplemental OCR is omitted and the native observation continues to grounding and validation without being relabeled. Validated PNG/JPEG evidence uses ImageIO to verify the matching container, apply orientation, and produce one bounded in-memory PNG for local Vision and viewing; its OCR observations deliberately have neither page nor bounding-box coordinates. Decode or OCR failure rejects the extraction bundle. Zero/multiple source matches, unsupported evidence, fingerprint mismatch, and unresolved account identity remain unassigned and return `Needs attention`; the renderer cannot submit classification identity. The responsive renderer checkpoint now covers Vault create/unlock/lock, Add file, safe import feedback, unassigned evidence, document-ID-only routing, and a bounded PDF/image viewer. The Rust host decrypts and renders one requested PDF page or validated image in memory, returns only PNG-encoded pixels plus page position, creates no plaintext temporary file, and rejects locked, missing, unsupported, and invalid-page requests. CSV evidence instead receives at most the first 200 lines and 32 KiB of UTF-8 preview plaintext with total counts and a truncation flag; a small file within both caps may appear in full, but the renderer never receives a raw original-file byte payload or unbounded content. Core Graphics now also derives protected-PDF state directly from the encrypted Vault file. A verified `Use once` password stays only in a zeroizing, document-scoped Rust session cache and is cleared on manual/system lock; `Update saved password` reaches the existing crash-reconciled Keychain path only after local PDF unlock succeeds. Verified protected text-layer statements use the same in-memory native extraction and routing path; malformed or still-locked PDFs remain fail-closed. The renderer receives only a narrow configured-source choice of ID, display name, and saved-password availability, uses it only to scope the credential but never assigns the document. Closing or locking removes password input, document names, and rendered page pixels and prevents stale async completions from restoring them. Manual and fifteen-minute inactivity locking now move the renderer into a fail-closed Vault gate before waiting for the privileged lock command; command failures reconcile the actual Vault status before the unlocked UI can return. Keyboard, pointer, touch, and wheel activity restart the fixed inactivity deadline. macOS sleep and user-session resignation mark the host session system-locked, reject queued unlocks through a monotonic generation, synchronously drop the Rust-only store, and only then notify the renderer. Explicit `Remember on this Mac` stores only the master key in macOS Keychain behind the Rust boundary, checks only entry presence during startup, offers user-initiated Keychain unlock without the password KDF, and can be removed without closing the current Vault. Unavailable, malformed, or unverified credentials preserve password unlock as the safe fallback without exposing secret values to the renderer. Canonical `statement_secret_refs` stores only a deterministic device-local storage key plus recoverable `pending_save`, `saved`, or `pending_delete` state; it never stores the password. Unlock and command reconciliation finish interrupted cross-store transitions, while production Keychain deletion propagates OS failures instead of clearing SQLite early. Host-confirmed source deletion commits the audit decision and tombstone before removing the encrypted blob; startup reconciliation removes a blob left by a crash, a missing or unverifiable blob becomes `Missing`, and exact-hash restoration of a user-deleted file requires a second host-owned confirmation. `Save a copy` is a separate document-ID-only host action: after an explicit warning and native save picker, Rust decrypts the original source from the Vault and atomically writes it outside the Vault through a private same-directory temporary file. Cancellation and pre-rename failure leave no partial destination; original PDF password protection, when present, remains part of the exported PDF. A general read-only source boundary now exposes only Money Source ID, display name, and source type; the renderer loads routed documents only for the selected source, keeps unassigned evidence in `Needs attention`, and uses the safe source name in routing feedback. Source creation/editing and full source-detail navigation remain deferred. A host-owned save action writes a self-contained `CCREC001` bearer recovery file outside the Vault and records only versioned configured state plus its SHA-256 fingerprint in the Vault. Initial setup remains non-blocking: the unlocked main surface keeps an actionable `To do` banner until both writes succeed. Recovery import remains deferred to `backup-release`; real provider packages/AI and source detail/Documents remain outside the completed slice.

- The parser evidence contract is accepted: extraction/OCR produce job-scoped observations, a mandatory AI normalizer produces one structured proposal shape, and each record persists one bounded validated raw source object plus a validation summary rather than a field-evidence graph. Dates do not receive invented timezones, and Debit/Credit remains separate from signed source-account balance movement.
- Database migrations grow by vertical slice. The synthetic core keeps many-to-many `match_edges` because two bank-side records linking through one canonical transfer event is a core query, while speculative evidence-reference tables, identifier machinery, indexes, and fixed benchmark sizes are excluded.
- The `document-normalizer-runtime` evidence slice is complete. Single-pass structured normalization is selected for initial implementation in a Tauri-controlled bundled Node sidecar; ToolLoopAgent and Pi Agent Core remain unselected until qualification fixtures demonstrate a material advantage. Full Pi Coding Agent is excluded, the sidecar is not treated as a sandbox, and users install no separate runtime.
- The `vault-security-validation` evidence slice is complete. Its merged macOS CI gate and independent reviews accepted `CCENV001` version 1, both versioned Argon2id wrappers and the 750 ms selection rule, source-scoped Keychain password behavior, memory-only Core Graphics PDF rendering, tombstone-first deletion recovery, and inactive-Vault atomic locator switching. The `vault-manual-import` and mock-only `cloud-ocr-provider-contract` slices are complete. The active `cloud-ocr-transport` slice adds only a reusable `packages/ai` executor behind an injected fetch boundary with deterministic mocked transport tests; it does not add credential storage/loading, app wiring, or a live request.
- Phase 1 supports macOS `arm64` and `x86_64`; Windows is Phase 2. Current end-to-end desktop, Vault, Keychain, and sidecar evidence exists only on `arm64`. Intel setup routing is test-covered, but a real `x86_64` build/runtime/security pass is still required before support can ship.
- The evidence-lifecycle/security grill is complete. `source_documents` also owns the encrypted-file registry/tombstone in MVP; there is no separate `vault_files` table. Source-file deletion retains records and ledger navigation; normal PDF/image viewing exposes only rendered pixels, bounded CSV viewing may expose preview plaintext to the renderer, and only explicit `Save a copy` exports the original source file outside CanCan.
- The acquisition design is inbox-first. Imported files and bounded canonical Gmail message envelopes share `source_documents`; source/account choice may wait for trusted classification. The evidence-only `local-inbox-readiness` slice can prove the local/iCloud stable-capture protocol without authorizing production behavior; `local-inbox-automation` adds the selected folder and deterministic statement-coverage prompts only after that evidence and the core review UI complete. A future native iOS Share Extension remains a thin intake companion gated by a separate feasibility slice; it does not authorize mobile ledger sync.
- Vault password wrappers use versioned Argon2id profiles, with the RFC 9106 64 MiB profile preferred inside a 750 ms supported-Mac budget and the OWASP 19 MiB minimum as the only accepted fallback. Keychain keeps the normal remembered unlock path fast. One optional PDF password per Money Source is also stored in Keychain and excluded from backup.
- New-device restore validates a new Vault before atomic switch, restores non-secret data, and opens a resumable Setup Checklist for Gmail, AI, statement passwords, remembered unlock, and backup target.
- Recovery-file saving may be deferred during initial setup; the app must keep the recovery action visible and accurately show that recovery is not yet configured.

## External setup checkpoints

No user-owned external account or credential blocks `vault-manual-import`. CI and deterministic development use synthetic/redacted documents and a mock model until the local storage, job, and sidecar boundaries are ready.

- Before the first opt-in live-AI smoke test, the user chooses a supported AI provider, creates their own API key, and enters it through CanCan setup or an untracked local override. The key must never enter Git, fixtures, logs, or CI. Provider choice and the exact disclosure remain blocked by the AI-consent work; do not request a key earlier.
- Before live Gmail development, the user creates a separate Google Cloud development/test project, enables Gmail API, configures a Desktop OAuth client, and adds explicit test users. Mocked Gmail work may precede this. Transaction-notification body capture also waits for the separate body-access disclosure and consent contract.
- Before public Gmail availability, the user must provide the public app identity, domain ownership, privacy/support contacts, production Google Cloud project, and verification submission materials. Restricted-scope verification is a later release workstream and should not be started before the running data flow and disclosures are reviewable.

Do not implement behavior covered by an active blocker. A ready slice may use a spec for its explicitly unblocked outcome without implementing that spec's blocked release, security, privacy, or product behavior; the generated slice context is the executable boundary.

## Current scope guardrail

Do not start API trading, payments, bill pay, mobile or multi-device implementation, full budgeting, tax reporting, autonomous financial advice, or external market-data/FX fetching before the core evidence/reconciliation loop works and the relevant canonical spec changes. The documented thin iOS intake direction is design-only until its feasibility slice is authorized.
