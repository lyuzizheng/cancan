# Implementation Slices

This is the machine-checked implementation sequence for CanCan. Coding agents use a slice ID to load the smallest reliable spec set instead of reading every canonical spec.

Rules:

- Keep the table columns unchanged; harness scripts parse it.
- A slice cannot enter production implementation while any listed blocker remains active.
- Status is `blocked`, `investigating`, `ready`, `in_progress`, or `completed`.
- `investigating` permits only the bounded disposable evidence work named by that slice's test gates. It does not permit production implementation or downstream work.
- A slice may become `ready` only when its active blockers are removed and every dependency is `completed`.
- Use exact area names from `docs/alignment-temp/alignment-progress.md`.
- `Test gates` names evidence categories, not invented shell commands.
- Update this plan when a blocker is resolved, a real package/command exists, or implementation evidence changes the sequence.

## Two-feature execution plan

The business and technical contracts live in the canonical specs, not this plan:

- `review-ledger-backend` and `review-ledger-ui`: [production review and ledger backend boundary](../specs/0005-review-and-commit-policy.md#production-review-and-ledger-backend-boundary)
- `local-inbox-backend` and `local-inbox-automation`: [production local Inbox boundary](../specs/0017-evidence-documents-source-ux.md#local-inbox-backend-production-boundary)
- shared durable jobs: [job engine and error model](../specs/0015-job-engine-error-model.md)
- Kimi renderer ownership: [Command Center component strategy](../specs/0006-command-center-ui.md#component-library-strategy) and [design-system implementation ownership](../specs/0008-design-system.md#implementation-ownership)

Delivery history (the table above owns live status and the later hardening/coverage split):

1. `review-ledger-backend` owns read models/contracts, review decisions and durable commit, and historical relationships plus reversal/replacement. `review-ledger-ui` is the Kimi renderer integration over those frozen contracts.
2. `local-inbox-backend` followed the review host boundary and delivered root authorization, stable scan/shared ingest jobs, and a provisional deterministic coverage fixture.
3. `local-inbox-automation` integrated the frozen host contracts. `post-pr41-hardening` now corrects the concrete implementation/evidence gaps, while `statement-coverage` is a separate later feature.

Backend and Kimi may work in isolated worktrees after the presentation contract for a checkpoint is frozen. Keep one source-writing agent per worktree, rebase the Kimi branch onto the accepted backend contract before integration, and let Kimi choose renderer structure/dependencies/Figma usage. Adjacent checkpoints may share one pull request only when the diff remains small and independently verifiable.

## Design grill checkpoints

Broad design grilling is paused only until implementation evidence can make the questions concrete:

1. After `synthetic-core-flow` completes and before `vault-manual-import`, run the bounded document-normalizer runtime spike and one grouped 5-10 question round covering evidence lifecycle, production vault/file security, runtime evidence, and any contradictions exposed by the synthetic flow. Patch each accepted answer into its canonical spec in the same session.
2. After `review-ledger-ui` completes and before public OAuth or release work, run one grouped 5-10 question round covering public identity/domain/support contacts, Gmail consent and verification claims, license, signing/notarization, updater-key custody, release channels, and community governance. Do not reopen the accepted Phase 1 macOS dual-architecture and Windows Phase 2 scope without contradictory evidence.

Focused single-blocker discussion remains allowed when a ready boundary exposes one irreversible security, financial, or data-shape decision. Do not reopen already accepted decisions without contradictory implementation evidence.
